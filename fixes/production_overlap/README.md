# V1 生产与收液、纠缠同时运行

原流水补丁并行下单、收液和纠缠，却等整个备料窗口转换完成后才放行装配。本补丁在当前实际配方的剩余凝聚物需求已满足时放行生产，窗口内其他原液继续下单、搬入独立子网和纠缠。库存不足则暂停等料，材料够后自动放行；窗口耗尽后重新计算真实缺口。

保持当前配方的归一化凝聚物需求、蜂群需求等级和麦克斯韦门过滤检查。配方变化或节点异常时暂停装配，完成旧窗口已提交的申请和已确认原液转换后交回原控制器的配方、过滤及蜂群配置。不同配方不会直接沿用旧过滤。轮询无法保证拦截两个检查之间已发生的瞬时配方切换。

V2 修正同一配方运行阶段的蜂群需求变化：当前蜂群等级大于或等于新需求、数量至少64时直接继续，不把阶段变化误判为配方切换。低等级或低数量仍暂停，并输出具体原因。安装器可从原流水或已发布 overlap V1 原位升级，保留一份独立备份，不重复包围生产循环。这里 V2 是 **V1 控制器补丁的第二版**，不是实验版16节点控制器。

V3 不再把“发送放行命令”打印成已证实生产。发送后持续读取本脚本红石输出和节点状态，给硬件至少3秒反应：输出仍0但节点立即暂停，显示检查其他控制仓的红石信号；输出被改回非0，显示检查其他脚本或红石控制。诊断保存在 `pipeline.feedback` 并显示在 EVENTS，相同信息最多每15秒打印一次。不会强行反复覆盖其他控制源。可升级 V1/V2 或原流水。需要读到现场回读才能判断这次暂停来自哪条控制路径。

出现“原液申请尚未确认完成，禁止重复下单”时，恢复尚未通过旧请求核对，库存够料不代表申请句柄已经结束。`check_requests.lua` 只读列出未确认请求、对应计划/确认搬入量/主子网及场库存、CPU的 activeItems/pendingItems 中对应原液条目。保留 submitted 原样，不设置 done、不重下、不取消、不搬液或改变控制信号。CPU列表无对应原液并不能单凭一次快照证明申请完成，尤其任务不可读时；先用报告区分仍在合成与日志状态遗留，再核对现场任务。

安装范围是已装 `BEC_V1_PIPELINE_V1` 的 **V1 `/home/bec_auto.lua`**。保留大订单窗口、蜂群、样板、缓存、UI、地址配置和全部日志；不覆盖整份控制器，不修改 V2 已发布版本。缺少流水入口会拒绝修改。独立高速口缺失的流体仍走原来的顺序备料路径。

在 UI 按 **Q 正常退出**，等纠缠装置停机，再运行：

```sh
wget -f https://fastly.jsdelivr.net/gh/Alivn-chao/gtnh-bec-automation@main/fixes/production_overlap/patch_v1.lua /home/bec_patch_overlap.lua
lua /home/bec_patch_overlap.lua
lua /home/bec_ui.lua resume
```

安装器先唯一定位和 Lua 语法检查，再验证红石暂停输出、纠缠装置关闭及不活动，保留 `/home/bec_auto.lua.before-overlap-N`，写临时文件、flush、回读后替换；替换失败还原。重复安装不重复写入。

每个请求和搬液仍先落盘，再执行、记录完整返回结果。提前放行前记录生产可消耗材料这一状态。恢复核对已确认供液总量、场内库存、子网余液和当前配方消耗，按各原料一致的已完成配方数核对；只转换已确认余液再按真实库存继续。未知搬液结果、申请未确认完成、无法解释的数量差异仍保留日志并报告原因，不重放操作。

`build_patch.py` 从旧流水 helper 生成新 helper 并嵌入安装器；`test_overlap.py` 使用 Lua 5.2 执行直接库存模拟和实际 V1 控制器。覆盖同时下单、生产期间纠缠和供液、配方变化、未确认操作拒绝重放、退出恢复和库存守恒，以及安装、编译、备份、幂等。模拟通过不等于已在游戏硬件验证。
