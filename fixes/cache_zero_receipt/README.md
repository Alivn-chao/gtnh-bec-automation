# 缓存零搬运回执与手动转换后的恢复

实机缓存申请搬38992mB超时空金属时收到`false, 0`并保护暂停。用户随后手动开启
纠缠器，将原来已搬入的多种原液转换，子网仅余32mB超时空金属；用户明确确认
旧6408000mB宇宙焊锡AE申请已完成。另一AE CPU只读库存持有36864mB超时空金属，
支持其他合成抢走可见原液的判断；没有取消其他CPU任务。

核对本机OpenComputers-1.12.61-GTNH.jar的InventoryTransfer$class字节码：
transferFluid在正常返回路径返回`moved > 0, moved`。所以`false, 0`明确表示本次
搬0，区别于nil/异常/false搭配正数。并行和旧顺序缓存均接受这个零回执，随后仍
核对子网未变化；计入zeroTransfers，不计入成功搬入量，也不留下失败搬运条目。
其他未知回执及库存不符仍停止，不重复搬运。AE任务结束但始终没有收获的原守卫保留。

新增cache_zero_recover.lua用于明确零回执的人工核对，不下单、不搬液、不启停机器。
它要求整组空闲、暂停、关闭接单及纠缠器停机，核对旧意图/零回执、所有前序回执与
secured、现有原液不超过已确认搬入量；run还要求操作者确认所有旧缓存AE任务结束。
归档并逐字核对原记录后，保存当前原液/凝聚物信用及原AE历史，不伪造旧任务自动完成。

新工作器仅接受此具名恢复凭据携带的非整批原液信用；子网必须与恢复快照一致。
它按现有凝聚物及32mB原液补实际差额，全部整批后再转换。有生产需求时优先只补齐
余数后交回；保留实际回执、任务状态、整组暂停和未知请求不重试规则。此恢复路径
需要cache_pipeline，缺失时保留原记录退出。其他未确认记录仍禁止启动。

285回归及20核心通过。新增6项覆盖零回执后继续收料且不多下单、假零回执伴随实际
搬运仍隔离、手动转换后部分原液信用、预览/缺少确认只读、未知回执拒绝、信用变化拒绝。
MCP安装包括lib/cache_pipeline.lua、runtime/cache.lua、lib/cache.lua及新恢复工具；
接线、配方、目标和生产控制器未改。私有证据在outputs/cache-fault-20261028。
旧缓存响应更新包不含cache_pipeline和新恢复工具，不能作为此修复的完整安装器。

手动核对入口（自动程序退出并保留原记录后使用）：

```sh
lua /home/bec_v2/cache_zero_recover.lua preview
lua /home/bec_v2/cache_zero_recover.lua run ae-finished
```

第二条仅适用于已确认旧AE申请结束且工具预览全部通过的明确零回执，不是通用重置命令。
