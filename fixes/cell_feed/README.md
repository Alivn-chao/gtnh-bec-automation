# 原料盘批次与物理并行

此功能为显式启用的 V3 扩展，沿用 `/home/bec_v2`。已有配置没有
`groups[N].cellFeed.enabled=true` 时，原接单流程不变。

## 本次接法

转运器西侧是缓存 ME 驱动器，东侧是生产 ME 驱动器，各只管理第 1 槽。
左右 AE 网络保持独立；右侧必须接到节点的物品输入子网。
OC 适配器地址不是驱动器的物品网络地址。

这套接法直接挂载整张盘，不通过 ME-IO 排空。转运器已实测能把空盘从
缓存驱动器移到生产驱动器并原路返回。盘内清单可通过
`getStackInSlot(...).getAvailableItems` 读取；总数是 `storedItemCount`。

## 批次流程

1. 每秒检查缓存盘是否非空，第一次有料后开始 10 秒收集窗口，不因继续到料重置。
2. 时间到且整组空闲后，关闭接单、保持立即暂停，移动整张盘。
3. 搬盘后读取固定清单，与已登记的普通输入匹配，确定完整配方份数。
4. 均匀分配给最多 16 台节点。每台接单前设置最小/最大并行为精确配额；
   例如 1000 份分成 8 台 63 份、8 台 62 份。
5. 逐台允许接单并立即关闭后续接单。等待实际暂停状态后核对真实并行与凝聚物需求。
   接单瞬间的 `crafting` 是允许的过渡态，保持暂停信号并继续等待。
6. 全部配额确认且原料盘为空后，空盘返回缓存端，再交给原控制器统一备料和放行。
7. 完成后恢复接单前的并行设置。下一批的收集计时可在本批生产期间开始。

`maxParallelPerNode` 是自动配额上限，不是“保证可用”的硬件能力。
真实接单仍受机器结构、供电和输入条件约束，以实际并行回读确认。
总量超出所配置上限、混入别的配方、配方匹配不唯一、NBT 原料或非消耗输入，
均保留盘和记录，不猜测或自动拆解未知投料。

## 检查与软件阶段等待

整批身份和每台实际配额在接单时验证。默认运行中使用固定批次快照，保留每台的状态和
蜂群需求读取；已实际证明完整的凝聚物消耗不反复读取，需求/并行也不重复全扫。
换蜂与最终完成仍使用原来的完整核对。

观察到先行节点需求变化时，用现有立即暂停信号让它等待仍在原阶段的节点。
全组进入相同新需求后再统一换蜂。这是 OC 回调间的软件等待，不保证精确停在
游戏 tick 的阶段边界。极短配方在两次回调间跨越多个需求时，退回原实时整组策略，
避免猜测阶段或留下停住的节点。不需要移除原有立即暂停控制仓。

已经验证的固定批次可另启用 `groups[N].cellFeed.representativeChecks=true`。
此时只从实际并行最多的未完成节点读取配方需求和蜂群需求；并行相同选最后放行的
节点。配方总需求和总并行取接单时确认的固定记录，不再因一次逻辑查询展开全组。
仍逐台检查状态、备料/换蜂时的暂停输出、真实消耗与最终完成，不能拿代表节点的
消耗乘以节点数。蜂群实体数量、IO 搬盘回读和观测阵列识别检查保持原有规则。

代表节点需求变化时读取其 `getRecipeSteps` 阶段表和 `getWorkProgress`；阶段交接
期间只读取其余节点的进度，让先到节点保持立即暂停，等其余节点到达相同进度边界
后再统一换蜂。阶段表只在本批内复用，重启重新确认。需要所有节点支持这两个原生
方法，配置验证会检查；没有启用此选项的既有接单模式保持原行为。

## 中断和恢复

`state/group-N/cell-feed.journal` 记录搬盘、参数设置和接单检查点，写前意图、
写后回读，并保留 `.previous`。不能删除记录强行重跑。
未知搬盘回执或未确认参数操作不自动重放，普通重启也不会自动重放未完成批次。

`cell_feed.new(..., true)` 仅供显式核对后的接单阶段修复使用：只接受
`waiting-node`、无 pending、原接线、整组关闭接单并暂停、已接单节点配额和
完整需求一致且凝聚物消耗为零、余下盘内清单精确等于原批次减去已接单份数。
它不重新搬盘，也不让已经接到配额的节点再次接单。正常引擎不调用此修复入口。

源文件在 `reinstall_v2/files/lib/{cell_feed,fixed_batch,representative}.lua`，调度接入 engine/cache，
配置检查接入 config，生产快照接入 bridge/controller。此模式需要配套模块，
不能仅复制新 Lua 文件后启用配置。旧三文件 V3 更新器不是本模式的完整安装器。

## 日常启动

已有网页时点右上角“启动自动化”；要停止时用网页“暂停”。只有退出网页程序后，
才在 OC 的 OpenOS 命令行重新打开：

```sh
lua /home/bec_v2/main.lua web
```

然后在网页点“启动自动化”。目录名仍为 `bec_v2`，即使已经安装 V3 优化也是如此。
同一面板只运行一份网页服务；提示已经运行时使用已有页面。正式网页“启动”会
重新启用暂停的节点调度；仅打开页面不会自行生产。原料盘有未完成/不明回执记录
时，重新打开可能拒绝启动，应保留记录核对，不能把这条命令当清状态指令。

AE 投料与网页自动化是两个独立开关。恢复已接单批次可以保持 AE 投料暂停；需要
连续接后续新料时，必须保证样板投料只进入左侧缓存网，右侧生产网保持隔离。

回归：`python reinstall_v3/run_tests.py`。模拟测试覆盖搬盘后计数、均分、整组空闲、
全部接单后才开工、消费证明、阶段等待、过渡状态、部分失败与显式恢复；模拟耗时
不是 Minecraft 性能测量。

## 2026-10-25 实机验收

用户提交 16 个原始屏蔽层。缓存盘共 5 类 / 368 件原料，搬盘后匹配
`gregtech_gt_metaitem_03_32307_1.dat` 的 16 份配方。接通右侧 AE 子网后，
16 台节点分别接到 1 份，整组放行完成；每台均有完整凝聚物消耗证明。
原料盘排空后回到缓存侧，生产驱动器为空，16 台全部空闲且关闭接单，
最小/最大并行已恢复到接单前的 1/256。

游戏中 `diagnostics/cell-feed-completed-20261025.dat` 保存完整收尾证明。
本轮还修正了真实接单瞬间的 `crafting` 过渡态；修复时严格验证
第一台 1 份已接单、其余 15 份仍在盘中、零凝聚物消耗，继续原批次，
未重复搬盘和接第一份料。

本轮验证了 16 台等配额生产。不同配额的等待策略目前通过模拟验证，
尚未通过新的不等配额游戏订单验收。178 项回归与 20 个原核心场景通过。
