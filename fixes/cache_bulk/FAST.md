# V2 空闲快速补库

用户反馈没有配方时仍不补库，多项库存未达5000000却显示“预缓存完成”。V1 priority将busyCPU任务对象读取失败视为配方存在，会无期限跳过补库；缓存UI又沿用上一轮完成文本，且每次强制绘图/翻页扫描配方目录。没有新的现场日志，不能声称这些已被确认为该服务器本次停顿的全部原因。

`patch_fast.lua`升级已安装的CACHE_PRIORITY_V1，保留配置和所有日志：

- 取消固定16桶分段，独立ME缓存器高速取液直接补单种完整缺口，最终库存目标维持用户配置值。
- 配方优先只由节点实际非空需求/运行状态，或AE CPU明确返回的登记产物任务触发。不可读的busyCPU记录告知一次，未确认配方时继续补库。确有配方时显示具体让位原因。
- 节点offline/unpowered/nanite不足/paused但没有实际需求时，生产控制器允许尝试后台补库；缓存模块仍检查节点安全状态、暂停输出、GEN启停/库存/搬液和申请结果。
- 保留V1途中配方优先交回和持久化规则。已提交AE请求先确认done、已搬入缓存原液转换完才交回；完整大额原液已搬入时转换可能仍较长，本升级没有并发运行两个纠缠控制器或丢弃缓存原液。
- 缓存UI展示收液/转换/等待/配方让位、本轮完成和按真实库存判断是否达标，不以旧完成文本冒充全部达标。展示库存2秒缓存，配方名称登记60秒刷新，翻页不重新扫描，R明确刷新。缓存目标修改后按新target比较。

正常Q停止生产后下载patch_fast.lua到/home/bec_patch_fast.lua并执行，再lua /home/bec_ui.lua run。三文件全部定位/语法检查后写临时文件，唯一备份、flush回读；后续文件替换失败时逆序还原全部已替换文件。兼容现有流水生产补丁。不删除/重置任何journal或重新下成品订单。

生成器 `build_maintenance.py`基于V1优先级源码输出 `bec_cache_fast.lua`和安装器；旧文件保留作为升级基准。Lua5.2 `test_fast.py <actual snapshot home dir>`覆盖实际cacheUI/auto+pipeline语法、第三文件失败全部回滚/重试/重复/日志保留、空闲128016mB一次搬完、不可读CPU继续补、确有配方让位、途中AE请求先确认/安全交回、未达库存完成状态和actual embedded绘图/翻页复用读取/R刷新。都是模拟，实际安装后需看当前状态/日志确认其他硬件或队列阻塞因素。
