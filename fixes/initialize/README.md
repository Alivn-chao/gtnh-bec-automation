# 初始化与 CPU 持续等待

用户要求的是归档旧运行状态后重新开始投料，并确认起初原液申请没有成功、原因是无空闲 CPU。本补丁把 Z 改为“初始化 / 重新投料”，并覆盖此前遗漏的顺序供液和后台缓存等待路径。

已复现上一版重置的确定错误：`production_reset/reset.lua` 每轮都断言约束场库存加子网原液等于旧预期。纠缠器先取走输入、稍后输出期间，该总和会暂时减少；组件读取跨越一次转换时也可能读到不同时间的快照。旧测试把输入扣除和产物增加模拟成一次原子操作，未覆盖这个间隔。新测试让输入立即扣除、输出延迟两秒，旧重置确实误报“数量不守恒”，初始化能够等待真实产物到达。这解释了截图命中的代码路径；具体服务器每种流体的变化仍以初始化现场记录为准。

CPU 问题：已有 cpu_wait 补丁只更改并行高速供液；缺高速口时的顺序路径和后台缓存仍有固定 1800 秒收料/合成等待超时、提交失败直接抛错。现在三个路径都在 CPU 全忙时保持服务运行，空闲后再提交。顺序/缓存中明确提交前失败记录为 rejected，显示手动申请及数量，继续收料；真实成功任务不因耗时长而超时。生产高速路径已有库存够当前配方时继续生产、纠缠和等待并行进行。物料不足时节点仍需等待供料，服务不会因此进入故障暂停。

## 安装

先 Q 退出 UI，下载并运行 `patch_v1.lua`，再 `lua /home/bec_ui.lua resume`，在当前故障页按 Z。需要已有缓存重置 V3 面板，可直接升级上一版“确认未下单”按钮，也支持没有生产重置 V1 的缓存 V3。若缺少 CPU 等待补丁，安装器先补装；随后修改实际生产控制器、缓存程序（存在时）和 UI，语法验证、唯一备份、flush/readback、替换失败回滚。CPU 前置补丁若单独安装成功，会保留其升级。

安装阶段不改运行日志或机器。已安装的蜂群、批次切换及其它控制器修复保留。

## 初始化行为

1. 按原文备份生产、缓存、旧缓存放弃/重置及失败生产重置记录。允许旧账缺失、陈旧或损坏，备份不是继续运行的前提账目。
2. 暂停节点、关闭纠缠器新转换、清除主网旧供液配置。等待现有转换完成，读取停稳后的真实场库存和子网原液。
3. 子网尚有原液时先转换现有物料；允许活动转换期间原液已扣而产物未入库，直到子网空、纠缠器 inactive 且库存读数稳定。不会按旧计划搬运或重放旧 pending 转移。真实机器 30 秒 inactive 且原液完全不减少时，显示具体剩余流体和数量，便于检查供电/输入仓/批量。
4. 将旧生产/缓存/重置状态归档，创建全新的 watching 会话，requests/transfers/target 为空，不继承旧供液计划。原控制器 resume 从当前机器配方和真实库存重新计算缺口、重新投料。

配置、登记配方、组件绑定、缓存目标、场内凝聚物和蜂群存储盘保留；蜂群实际搬盘日志仍由其模块处理。旧 AE 申请原文在备份中，不伪装为已完成。本初始化按用户已确认旧原液申请未成功的现场授权实施，不能推断其它场景里已运行的外部任务也未成功。

每次生成 `/home/bec_initialize-N.dat`，记录原日志备份位置、初始化阶段、现场库存、当前需求/消耗、上一版重置 expected（可读时）、完成后的库存。备份后缀 `.before-initialize-N`，旧活动日志另存 `.retired-initialize-N`。Q 中断关闭纠缠器并保留实物；再按 Z 会新建本次现场快照，不要求旧重置进度继续相等。

## 验证

运行 `python fixes/initialize/build_patch.py` 生成单文件安装器，`python fixes/initialize/test_init.py` 运行 Lua 5.2 模拟。

17 项测试包括：旧守恒误报复现、延迟转换/跨中断产出、旧 pending 和错误 expected 归档后重建、真实余料转换、重复初始化、失败回滚、机器真实停滞提示、真实控制器仅补当前缺口完成一份、最新 UI 鼠标 Z 初始化并 resume 一次、前置补丁补装及幂等、顺序/缓存忙 CPU 超过旧超时继续等待、提交前失败手动供液、已安装并行代码在全部 CPU 忙 7000 秒期间先消耗现货生产、空闲后自动下单完成其余配方。

这些是模拟验证，尚未在用户游戏环境实测。
